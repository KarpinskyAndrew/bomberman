This document describes how the Go game server is built and how clients talk to it. The main design goal is **minimal ping and perceived delay**.

---

## 1. Design Principles

1. **The server is authoritative, and the client predicts.** The server owns the truth. The client simulates its own player immediately and corrects itself when the server disagrees.
2. **Get packets close to players.** v1 runs one server in Frankfurt, which is central to the EU player base. v2 runs game servers in several regions and routes each player to the nearest one. Both use Google's Premium Tier backbone.
3. **Never block the tick.** No I/O, locks, database calls or allocations happen in the simulation hot path, and a slow client never slows down an arena.
4. **Small, binary, unbuffered.** Hot-path messages are compact binary frames sent with Nagle disabled and without compression.
5. **The transport can be swapped.** The protocol is defined above the transport: WebSocket in v1, with WebTransport datagrams added in v2.
6. **Measure everything.** RTT, jitter, tick duration and prediction corrections are tracked as first-class metrics.

## 2. Latency Budget

The example assumes a player in the same region with a **30 ms RTT**.

| # | Stage | Typical | Notes |
|---|---|---|---|
| 1 | Key press → client sim tick | 0–16.7 ms | Client simulates at 60 Hz |
| 2 | Client → server (one way) | 15 ms | RTT / 2 |
| 3 | Server input buffer | 0–17 ms | Adaptive target of 1 tick (§6.2) |
| 4 | Wait for next tick + simulate | ~8 ms + < 1 ms | 60 Hz tick, input applied next tick |
| 5 | Wait for outgoing frame | 0–17 ms | Events are sent on the **same tick**, snapshots every 2nd tick |
| 6 | Server → client (one way) | 15 ms | RTT / 2 |
| 7 | Interpolation delay (remote entities) | ~50 ms | Adaptive 35–150 ms based on jitter (§6.4) |
| 8 | Render | 0–16.7 ms | Next `requestAnimationFrame` |

Resulting perceived latency:

| What | Latency | How |
|---|---|---|
| Own movement on screen | **≤ 1 frame (≈ 8–17 ms)** | Client-side prediction |
| Own bomb appears | **≤ 1 frame** as a "pending" bomb, confirmed after ≈ 1 RTT + 1 tick | Bomb prediction |
| Explosion / wall destroyed / pickup | ≈ RTT/2 + ≤ 1 tick after it happens on the server | Events are sent immediately |
| Remote player / alien position | ≈ RTT/2 + interpolation delay (≈ 65–80 ms behind the server) | Snapshot interpolation |

**Region targets:** p50 RTT ≤ 40 ms and p95 ≤ 80 ms for players inside a served region.

### 3.2 The simulation package (`internal/game`)

The simulation is **pure and deterministic**: `State + []Command → State' + []Event`.

- No `time.Now()`, goroutines, I/O or global randomness.
- One PRNG per match (`math/rand/v2` PCG, seeded from the match seed).
- **Integer math only.** Movement progress is an integer tick counter, so floats never appear.
- A fixed update order every tick:
  1. Apply player commands, in slot order.
  2. Move players.
  3. Run alien AI decisions, then move aliens, in id order.
  4. Count down bomb fuses and resolve explosions. Chain reactions are processed through a queue within the same tick.
  5. Apply fire damage to players and aliens.
  6. Check alien contact.
  7. Handle pickups.
  8. Spawn drops whose fire has ended.
  9. Spawn aliens (portals).
  10. Advance sudden death.
  11. Check win conditions.
- Entities live in **fixed-size arrays/slices** that are preallocated per match: grid `[21*21]Tile` (sized for the largest arena; smaller arenas use the top-left `size × size` part and a `size` field, so the array never changes shape), players `[4]Player`, aliens `[16]Alien`, bombs `[32]Bomb`, items `[64]Item`. Steady-state ticks therefore make **0 allocations**, which is enforced by `testing.AllocsPerRun` benchmarks.
- **What the client re-implements (the prediction subset):**
  - `canEnter(tile)`, `stepMovement(player, cmd)` (start/continue/turn/stop, 9 ticks per tile) and `canPlaceBomb(player, tile)`.
  - That is roughly 300 lines of TypeScript in `web/src/game/sim/`.
  - Everything else is **never predicted**: fuses, explosions, chain reactions, damage, pickups, aliens and sudden death. The client only shows these when the server's events arrive.
- **Shared rule test vectors, generated from Go:**
  - `go run ./cmd/vectorgen` runs the real `internal/game` code on scripted and randomized scenarios and writes `/protocol/testdata/rules/*.json`.
  - Each case contains `{ grid, bombs, player, commands[], expected[] }`, where `expected` is the per-tick `{x, y, dir, progress, bombPlaced}` of the player.
  - Coverage: walking into walls, bombs and other players, turning mid-tile, holding vs. tapping, bomb capacity, a bomb on an occupied tile, and walking off the player's own fresh bomb.
  - **CI checks:** a Go test regenerates the vectors and fails if they differ from the committed files, so Go rule changes cannot ship without updated vectors. Vitest then replays every case through the TypeScript port and must match tick for tick.
  - The golden vectors for the binary codec (§5.5) work the same way.
- **Rounds vs. matches:**
  - `internal/game` simulates **one round** (a pure state machine).
  - A small `internal/game/match` package holds the match logic: best-of-3 for ranked (round points, round wins, tiebreaks, forfeits), a single round for unrated, and match placement. It is pure and fully unit-tested.
  - The arena actor also owns the waiting room's 15 s **ready countdown** (SPEC §5.2). It is counted in ticks like everything else, so pausing and restarting it is deterministic.
  - The arena actor drives the sequence ROUND → ROUND_END → … → MATCH_END.
- **Replays:** seed + config + the ordered command log reproduce a round exactly. Logs can be uploaded to GCS for debugging (`match_rounds.input_log_uri`).

### 3.3 Arena actor (`internal/arena`)

Each arena is **one goroutine** that owns all of its state, so no locks are needed.

```go
func (a *Arena) Run(ctx context.Context) {
    const dt = time.Second / 60
    next := time.Now()
    for {
        select {
        case <-ctx.Done():
            return
        case ctl := <-a.control: // join, leave, ready, kick... (low frequency)
            a.handleControl(ctl)
            continue
        default:
        }

        a.collectCommands()        // pop ≤1 command per player from its input buffer (§6.2)
        events := a.sim.Step()     // deterministic step, events appended into a reused slice
        a.publish(events)          // hand off to per-connection writers (non-blocking)

        next = next.Add(dt)
        if lag := time.Since(next); lag > 5*dt { // fell far behind: resync, record overrun
            a.metrics.TickOverrun.Inc()
            next = time.Now()
        }
        a.sleepUntil(next)         // timer-based, does not drift
    }
}
```

- **Fixed timestep** against an absolute schedule (`next += dt`), so the tick rate does not drift.
- Inputs arrive from connection reader goroutines into **per-player lock-free ring buffers** (SPSC). The arena never blocks on them.
- **Broadcast:**
  - The shared snapshot body is encoded **once per tick per arena**.
  - Each connection gets a tiny per-client header (its `ackSeq`) followed by the shared body.
  - Frames are handed to connection writers through the *coalescing outbox* (§3.4).
- **Events:**
  - Every tick's events get arena-scoped `eventSeq` numbers.
  - Internal observers (MatchRecorder, telemetry) process them on the arena goroutine without doing I/O.
  - Encoded event frames are also kept in a **10 s replay ring buffer** used when a client resumes.

  See [Events §3](./EVENTS-AND-MESSAGING.md#3-real-time-game-event-handling-class-a).
- **Persistence:**
  - The game server **never writes to PostgreSQL**.
  - When a match ends, MatchRecorder builds a `match.finished` domain event, and the EventPublisher goroutine publishes it to **Pub/Sub**, using a bounded local spool if publishing fails.
  - The rating worker persists the match and applies ELO.
  - The game loop never waits on the queue or the DB. See [Events §6](./EVENTS-AND-MESSAGING.md#6-producers).

### 3.4 Connection handling

Each connection has 2 goroutines:

| Goroutine | Job |
|---|---|
| **Reader** | Reads frames, validates them (size ≤ 1 KiB, known type, monotonic `seq`), applies rate limits and pushes commands into the player's input ring buffer. |
| **Writer** | Drains the **coalescing outbox** and writes frames with a 2 s write deadline. |

**Coalescing outbox:**

- The arena does not append to an unbounded queue. Each connection holds:
  - `pendingEvents`, a bounded byte buffer of encoded events, and
  - `latestSnapshot`, a pointer that is replaced, never queued.
- When the writer gets a chance, it sends **one frame** containing all pending events plus the latest snapshot.
- A slow client therefore skips stale snapshots instead of building up lag.
- If `pendingEvents` overflows (more than 64 KiB, roughly 2+ s of stall), the client is disconnected and resynced with a full state message when it reconnects.

**Socket and runtime settings:**

| Setting | Value |
|---|---|
| TCP_NODELAY | On (Go's default for TCP). It is never turned off. |
| WebSocket compression (`permessage-deflate`) | **Disabled**. Frames are about 100 bytes, so compression only adds CPU time and latency. |
| Heartbeat | App-level `PING`/`PONG` every 2 s. It measures RTT and clock offset (§6.5) and keeps load balancers from closing idle connections. |
| GOMEMLIMIT | 80 % of the container memory |
| GOGC | Default |
| Profiling | `net/http/pprof` on an internal-only port (reached through the IAP SSH tunnel in prod). CI benchmarks fail on regressions in ns/tick or allocs/tick. |

### 3.5 Capacity estimate (per 2 vCPU instance)

| Item | Estimate |
|---|---|
| Simulation | ~20 µs/tick per arena with aliens → 200 arenas × 60 Hz × 20 µs ≈ **0.24 CPU** |
| Encoding + syscalls | ~800 players × (30 snapshots + ~10 event frames)/s ≈ 32k writes/s ≈ **0.5–0.8 CPU** |
| Headroom | Kept for GC, the reader goroutines and spikes. Load testing with `cmd/bots` validates the estimate in M3. |

### 3.6 Networking code: build vs. buy

There is no Colyseus-style framework in this design. Libraries handle the low-level transport, and the game-specific parts are written by hand. Most of what a framework would provide either is not needed (delta state sync: a full snapshot is about 120 B) or is game logic we would write anyway (arena lifecycle, best-of-3, ranked rules).

| Concern | Provided by | We write | Rough size |
|---|---|---|---|
| WebSocket server (handshake, framing, ping, close) | `github.com/coder/websocket` | – | – |
| HTTP routing, JWT | `gin-gonic/gin`, `golang-jwt/jwt` | Auth handshake on the socket (`AUTH` within 5 s) | ~100 lines Go |
| Connection reader/writer, coalescing outbox, rate limits | – | `internal/transport/ws` (§3.4) | ~400 lines Go |
| Binary codec | `encoding/binary` | `internal/proto` + `web/src/net/codec.ts`, golden vectors | ~400 Go + ~400 TS |
| Control messages | `encoding/json` | Message structs and dispatch | ~300 lines Go |
| Rooms / arenas / lobby | – | `internal/lobby`, `internal/arena` (game logic, needed with any framework) | ~800 lines Go |
| Reconnect and replay | – | `eventSeq` ring buffer, `arena.resume`, `resync` (§7) | ~200 Go + ~150 TS |
| Clock sync | – | PING/PONG offset estimation (§6.5) | ~80 Go + ~100 TS |
| Client socket wrapper | Browser `WebSocket` | Connect, backoff, heartbeat, message routing | ~250 lines TS |
| Prediction and interpolation | – | §6 (**no framework provides these**) | ~500 lines TS |
| WebTransport (v2) | `quic-go/webtransport-go` | Second `Conn` implementation | v2 only |

**Total:** roughly 2,000 lines of Go and 1,500 lines of TypeScript of networking code, about 2–3 weeks of milestone M3. The line counts are estimates. Arena and lobby logic make up the largest single part, and that part would exist with any framework.

**Keeping this small in v1:**

- Only WebSocket. WebTransport waits for v2 behind the `Conn` interface.
- JSON for everything that is not hot-path, so it is easy to debug.
- One game server instance in v1, so there is no cross-node routing yet. The gateway and join tickets come in v2.
- `cmd/bots` reuses the Go codec, so load tests cost almost no extra code.

## 4. Transport

### 4.1 v1: WebSocket (binary + text frames)

- `wss://<region-host>/play`. Over a socket that is already open, the first message must be `AUTH` with a JWT or a join ticket, sent within 5 s.
- Tokens are **not** put in the URL, so they never end up in load balancer or proxy logs.
- **Text frames (JSON)** carry low-frequency control messages: lobby, arena management, results. They are easy to debug and not latency-critical.
- **Binary frames** carry the hot path: commands, tick frames, ping/pong.
- **One socket for the whole session:** it opens on entering the lobby and is reused for joining arenas on the same server, so joining does not need a new TCP/TLS handshake. Moving to an arena in another region opens a new socket using a **join ticket** (§8.3).
- **Known limitation:** TCP **head-of-line blocking**. One lost packet stalls everything behind it for about one RTT. The coalescing outbox and the interpolation buffer reduce the effect, and WebTransport in v2 removes it.

### 4.2 v2: WebTransport (HTTP/3 / QUIC)

| Channel | Mode | Content |
|---|---|---|
| **Datagrams** (unreliable, unordered) | Snapshots and commands | Commands carry the last 3 commands redundantly, so losing a datagram does not lose input. |
| **One bidirectional reliable stream** | Events + control | Bombs, explosions, walls, items, eliminations, lobby. |

- **Fallback:** if `WebTransport` is unavailable or blocked (UDP filtered, unsupported browser), the client uses WebSocket automatically. Browser support, especially Safari, must be verified when this is implemented. The WebSocket path must always remain complete.
- **GCP constraint:** the external Application Load Balancer does not proxy WebTransport. Game pods are exposed through a **regional passthrough Network Load Balancer (UDP/TCP)**, and TLS is terminated inside the Go process. Certificates come from cert-manager / Let's Encrypt.
- **Server library:** `quic-go/webtransport-go`.
- The transport is hidden behind an interface, so arena code does not care which one is used:

```go
type Conn interface {
    SendReliable(frame []byte) error   // events, control
    SendUnreliable(frame []byte) error // snapshots (falls back to reliable on WS)
    Recv() (Frame, error)
    Close(code int, reason string)
}
```

## 5. Binary Protocol

- All binary frames are **little-endian**. The first byte is the message type.
- **Protocol version** is sent in `AUTH`. On a mismatch the server closes the connection with code 4001 ("client outdated"), and the client reloads.

### 5.1 Client → Server (binary)

| Type | Name | Layout | Size |
|---|---|---|---|
| `0x01` | `CMD` | `u8 count(1–3)`, then `count` × { `u32 seq`, `u8 bits` }, newest first | 6–16 B |
| `0x02` | `PING` | `u32 clientTimeMs` | 5 B |

`bits` layout:

| Bits | Meaning |
|---|---|
| 0–2 | Direction: `0` none, `1` up, `2` down, `3` left, `4` right |
| 3 | Bomb pressed this tick (edge-triggered) |
| 4–7 | Reserved |

The client sends **one `CMD` per client tick (60 Hz)**. On WebSocket `count = 1`. On WebTransport datagrams `count = 3` for redundancy.

### 5.2 Server → Client (binary)

| Type | Name | Layout |
|---|---|---|
| `0x80` | `TICK` | `u32 tick`, `u32 ackSeq`, `u8 flags` (bit0 = has snapshot, bit1 = has events, bit2 = has private events), [`SNAPSHOT`], [`u32 firstEventSeq`, `u8 nEvents`, `EVENT`…], [`u16 firstPrivSeq`, `u8 nPriv`, `EVENT`…] |
| `0x81` | `ROUND_START` | `u8 roundNo`, `u8 bestOf`, `u64 seed`, `u32 startTick`, `u8 config[16]`, `u8 size` (15, 17 or 21), `u8 grid[size × size]` (0 empty, 1 hard, 2 soft; at most 441 bytes), `u8 nPlayers` + spawn slots. Sent at every round's COUNTDOWN, because each round has a new map. Tick and `eventSeq` keep counting across rounds. |
| `0x82` | `FULL_STATE` | Sent on join or reconnect: grid + all bombs, fires, items, aliens, players + `tick` |
| `0x83` | `PONG` | `u32 clientTimeMs` (echoed), `u32 serverTick`, `u16 serverHoldUs` |

- A `TICK` frame is sent **every tick that has events** and **every 2nd tick (30 Hz) with a snapshot**.
- Events are therefore never delayed waiting for the next snapshot.

**`SNAPSHOT`:**

```
u8 nPlayers
  per player (10 B): u8 slot, u8 x, u8 y, u8 dirMoving (dir 3 bits | moving 1 bit),
                     u8 progress (0–255), u8 hp, u8 range, u8 bombCap,
                     u8 bombsActive, u8 flags (alive, invuln, connected, ...)
u8 nAliens
  per alien (8 B):   u16 id, u8 type, u8 x, u8 y, u8 dirMoving, u8 progress, u8 hpFlags
```

**`EVENT`** (`u8 kind` + payload):

| Kind | Name | Payload |
|---|---|---|
| 1 | `BOMB_PLACED` | `u16 bombId, u8 ownerSlot, u8 x, u8 y, u8 range, u32 explodeTick, u32 cmdSeq` (lets the owner match its predicted bomb) |
| 2 | `BOMB_EXPLODED` | `u16 bombId, u8 up, u8 down, u8 left, u8 right` (actual fire lengths; the client derives the tiles) |
| 3 | `WALL_DESTROYED` | `u8 x, u8 y` |
| 4 | `ITEM_SPAWNED` | `u16 itemId, u8 kind (1 health, 2 fire, 3 bomb), u8 x, u8 y, u8 source (wall/alien)` |
| 5 | `ITEM_TAKEN` | `u16 itemId, u8 slot` |
| 6 | `ITEM_DESTROYED` | `u16 itemId` |
| 7 | `PLAYER_HIT` | `u8 slot, u8 sourceSlot (0xFF none), u8 hpLeft`. Bomb fire only, since alien contact is an instant kill. |
| 8 | `PLAYER_ELIMINATED` | `u8 slot, u8 cause (bomb/self/alien/crush/disconnect/left), u8 killerSlot (0xFF none), u16 alienId (0 if not alien)` |
| 9 | `ALIEN_PORTAL` | `u16 alienId, u8 type, u8 x, u8 y, u32 appearTick` |
| 10 | `ALIEN_HIT` | `u16 alienId, u8 hpLeft, u8 sourceSlot` |
| 11 | `ALIEN_KILLED` | `u16 alienId, u8 killerSlot` |
| 12 | `SUDDEN_DEATH_TILE` | `u8 x, u8 y` |
| 13 | `BOMB_REJECTED` | `u32 cmdSeq`. **Private**: sent to the owner only, so the client removes its predicted bomb. |

- Fire tiles expire **implicitly** 30 ticks after `BOMB_EXPLODED`, so no event is needed.
- **Broadcast events** are numbered by a gap-free, arena-scoped `eventSeq`, and the events in a frame are consecutive from `firstEventSeq`.
- **Private events** have their own per-connection `privSeq`.
- `ackSeq` and the private section are the only per-client parts of a frame. The broadcast part is encoded once and shared.
- The client ignores events at or below the last sequence it applied and asks for a `resync` when it detects a gap. See [Events §3](./EVENTS-AND-MESSAGING.md#3-real-time-game-event-handling-class-a).

### 5.3 Control messages (JSON text frames)

| Direction | Types |
|---|---|
| C→S | `auth`, `lobby.subscribe`, `lobby.unsubscribe`, `arena.create` (incl. `ranked`), `arena.join` (`{arenaId}` / `{code}`), `arena.resume` (`{arenaId, lastEventSeq}`), `arena.leave`, `arena.ready` (`{ready: bool}`), `arena.kick`, `resync`. There is no `arena.start`: a match starts only through the all-ready countdown (SPEC §5.2). |
| S→C | `auth.ok`, `lobby.list`, `lobby.update`, `arena.state`, **`arena.ready_countdown`** (`{endsAtTick\|null, paused: bool, reason?: "player_joined"\|"not_ready"\|"player_left"}`, sent whenever the 15 s waiting-room countdown starts, pauses, restarts or is cancelled), `arena.countdown` (`{roundNo, bestOf, score}`), **`round.end`** (`{roundNo, winnerSlot\|null, draw, reason: "last_standing"\|"timeout_hp"\|"simultaneous", survivorsHp, placements, points, score:[{slot, roundWins, roundPoints}], matchDecided}`), `match.end` (`{matchId, mode, bestOf, winnerSlot\|null, draw, placements, rounds, stats, ratingPending}`), **`rating.updated`** (`{matchId, before, after, delta, tier, rank?}`), `server.draining`, `error` (`{code, message}`, e.g. `ranked_requires_account` when a guest tries to join a Ranked arena) |

### 5.4 Bandwidth estimate (4 players, 8 aliens)

| Direction | Payload | With WS + TLS + TCP/IP headers |
|---|---|---|
| Down: snapshot frames | ~120 B × 30/s | ≈ 190 B × 30 ≈ **5.7 KB/s** |
| Down: event frames | ~20 B × ~10/s | ≈ **0.9 KB/s** |
| Up: commands | 6 B × 60/s | ≈ 80 B × 60 ≈ **4.8 KB/s** |

- That is under 100 kbit/s in each direction, which works on any connection, including mobile tethering.
- Egress cost per player-hour is ≈ 24 MB.

### 5.5 Shared codec and tests

- `/protocol/PROTOCOL.md` is the source of truth. The codecs are written by hand in Go (`internal/proto`) and TS (`web/src/net/codec.ts`).
- `/protocol/testdata/*.bin` + `*.json` are **golden vectors**. Both test suites encode and decode them, so the Go and TS sides cannot drift apart.
- Fuzz tests run on the Go decoder (`go test -fuzz`) to harden it against malicious frames.

## 6. Latency-Hiding Netcode

### 6.1 Client-side prediction (own player)

The client runs its own player at **60 Hz** with the same movement rules as the server (the TypeScript prediction subset from §3.2, verified by the generated test vectors), using its local copy of the grid and bombs.

- Every client tick:
  1. Sample input.
  2. Create `cmd{seq++, bits}`.
  3. Apply the command locally.
  4. Store it in `pendingCmds`.
  5. Send it.
- When a snapshot arrives with `ackSeq`:
  1. Take the **server's** state for the own player.
  2. Drop the commands with `seq ≤ ackSeq`.
  3. **Re-apply** the remaining pending commands on top of the server state, which gives the corrected predicted state.
  4. If the result differs from what is on screen, **blend** visually over 100 ms instead of snapping. If the difference is larger than one tile, snap.
- Because the server consumes exactly the same command stream in the same order (§6.2), mispredictions happen only when the world changed in a way the client did not know yet, such as a remote bomb blocking the path. These cases are rare and small.

### 6.2 Server input buffer

- The server consumes **exactly one command per player per tick**. Speed hacks are therefore impossible: sending commands faster only fills the buffer, and anything beyond the cap is dropped.
- The buffer targets a depth of **1 tick**, adjusted to the measured arrival jitter (0–3 ticks):
  - If the buffer is **empty**, the server repeats the player's last held direction (without the bomb bit) and records an "input starvation" event.
  - If it is **too deep**, the server drops the oldest commands (but keeps their bomb bits) to catch up.
- `ackSeq` in each `TICK` is the last command `seq` the server consumed for that player.

### 6.3 Bomb prediction

- When SPACE is pressed and the local rules allow it (capacity and tile), the client immediately draws a **pending bomb** on the predicted tile, with a slightly translucent sprite and the fuse animation starting.
- The client matches the server's `BOMB_PLACED` by `cmdSeq`, after which the bomb becomes solid and its fuse syncs to `explodeTick`.
- On `BOMB_REJECTED`, or if no confirmation arrives within `RTT + 200 ms`, the pending bomb fades out.
- **Explosions are never predicted.** They always come from `BOMB_EXPLODED`, because chain reactions and hits are authoritative. As the fuse ends, the bomb sprite flashes faster over the last 0.5 s, so the explosion never comes as a surprise.

### 6.4 Interpolation (remote players & aliens)

- The client keeps a buffer of snapshots stamped with server tick and renders remote entities at `renderTick = estimatedServerTick − interpDelay`, interpolating tile + progress between the two surrounding snapshots.
- `interpDelay` = max(35 ms, 1.5 × snapshot interval + 2 × measured jitter), capped at 150 ms. It adapts smoothly by speeding or slowing local time ±5 %, never by jumping.
- If a snapshot is missing, the client extrapolates for at most 100 ms along the current direction (tile movement is predictable), then freezes.
- *Experiment (M3):* **dead reckoning within the current step** for aliens and remote players. Since a move between two tiles is fully determined once it starts, the client can render the current step with almost no delay and only correct on turns. This is enabled only if playtests show it looks smooth.

### 6.5 Clock synchronization

- Every `PONG` provides an RTT sample and a server tick.
- The client keeps the **lowest-RTT samples from the last 10** to estimate `serverTickOffset`, using an NTP-style filter.
- This estimate drives `estimatedServerTick`, the interpolation timeline and the fuse countdowns shown on screen.
- The ping shown in the HUD is the median RTT of the last 10 samples.

### 6.6 Event timing

- World events (bombs, fire, walls, items) are applied **as soon as they are received**. They are not delayed by `interpDelay`, so walls and fire appear as early as possible.
- Remote entities lag about 50 ms behind that. This is a deliberate, standard trade-off: the only visible effect is that an alien may appear to step into fire a fraction of a second "late". The damage itself is decided by the server.

## 7. Reconnect & Resilience

- **Session resume:**
  - On a network drop the client reconnects with exponential backoff (100 ms, 200 ms, 400 ms… capped at 2 s), then sends `auth` followed by `arena.resume {arenaId, lastEventSeq}`.
  - If `lastEventSeq` is still inside the arena's 10 s replay buffer, the server sends only the **missing events** plus the current snapshot. Otherwise it sends `FULL_STATE`.
  - The player's 15 s grace period (spec §4.8) is cancelled.
- **Server-initiated closes** (code 1001/1012, e.g. a game server restart during a v1 deploy, or a proxy recycling connections) are handled the same way: the client resumes **without showing a "disconnected" screen** if the resume succeeds within 1 s. Caddy's WebSocket proxy has no idle timeout for `/play`, and the 2 s heartbeat keeps the connection active anyway.
- **Draining (v2):** on `SIGTERM` a game pod:
  1. Marks itself `draining` in the directory, so it receives no new arenas.
  2. Sends `server.draining` to players in WAITING arenas, whose clients automatically re-join via Quick Play elsewhere.
  3. Lets running best-of-3 matches finish (up to about 10 min), using `terminationGracePeriodSeconds` up to the platform maximum. If the grace period is shorter than the remaining match, the match is aborted (`match.aborted`, unrated).
  4. Flushes the Pub/Sub publish spool, so every `match.finished` is acknowledged before the process exits.

## 8. Deployment Topology & Scaling

### 8.1 v1: one server

| Component | Configuration |
|---|---|
| Host | One **Compute Engine VM** (`e2-standard-4`) in **`europe-west3` (Frankfurt)**, running Docker Compose. Full stack and runbook: [CI-CD §6](./CI-CD.md#6-the-v1-server). |
| Edge | **Caddy** terminates TLS on :443 and proxies `/play` to the game server over the internal Docker network. This is the only proxy hop, and it is on the same machine. |
| Game server | One container. **No CPU limit** is set on it (CFS quotas cause tick jitter); the observability containers get limits instead, so they can't starve the tick loop. `stop_grace_period: 2m` for draining. |
| API service | One container (Gin + gRPC), behind Caddy and Envoy. |
| Data | PostgreSQL 17 container on the same VM. |
| Messaging | Pub/Sub topic `match-events` (+ DLQ). The **rating worker** container uses a **pull** subscription, so it needs no public endpoint. |

**Known v1 limitations:**

- A deploy that changes the game server image, or a VM restart, interrupts running matches. Such deploys happen in low-traffic windows (CI-CD §6.2).
- The VM is a single point of failure. Recovery is a VM restart, or a new VM from the latest disk snapshot.
- Database, game server and observability share one machine, so a heavy query or a Prometheus compaction could in theory cause tick jitter. `tick_jitter_us` (§9.1) shows whether that happens.

### 8.2 v2: multi-region GKE

Every service is deployed with its own **Helm** chart, from the same images v1 uses.

```
                  Player
                    │  (1) ListRegions → ping each region (§8.4)
                    ▼
     ┌────────── nearest region ───────────┐
     │  Passthrough NLB (TCP 443 + UDP 443) │
     │        │                             │
     │  Gateway pods (Go) ── route by ticket/arena ──► Game pods (Go)
     │                                      │   arenas in memory
     └──────────────────────────────────────┘
        │ arena directory / lobby pub-sub        │ match.finished (regional endpoint)
        ▼                                        ▼
  Memorystore (Redis), primary region     Cloud Pub/Sub (global) ──pull──► Rating worker (GKE)
                                                                              │
                                   game pods ◄── LISTEN rating_updated ── Cloud SQL PostgreSQL (primary region)
```

- **Regions (EU only):** `europe-west3` (Frankfurt, primary), `europe-west1` (Belgium), `europe-central2` (Warsaw). `europe-north1` is optional.
- **Game pods:** Autopilot with **requests = limits** (Guaranteed QoS) on a Balanced/Performance compute class. This avoids CFS CPU throttling, which causes tick jitter.
- **Gateway:** a thin Go relay that terminates TLS (WS and WT), validates the join ticket and forwards bytes to the game pod hosting the arena over the VPC. It adds about 0.2 ms. Gateways are stateless and scale on connection count.
- **Directory (Redis):**
  - Arena records: `arena:{id} → {region, pod, status, players, private, code}`.
  - A sorted set per region for Quick Play.
  - Lobby updates over pub/sub.
  - Game pods heartbeat every 2 s, and records expire after 10 s.
- **Autoscaling:** an HPA on the custom metric `arenas_per_pod` (target 150) together with CPU usage.

### 8.3 Join tickets

When a player chooses an arena, quick-plays or creates one, the API service or lobby picks the region and pod and issues a **join ticket**: a JWT valid for 30 s, signed with Secret Manager keys, containing `{playerId, arenaId, region, pod}`. The client connects to that region's gateway with the ticket, and the gateway routes it without any extra lookup.

### 8.4 Region selection (ping-based)

1. `RegionService.ListRegions` (gRPC, spec §6.1) returns `[{id, label, pingUrl, wsUrl, wtUrl}]`. In v1 the list has one entry.
2. The client sends 1 warm-up request (which absorbs the TLS handshake), then **5 `HEAD pingUrl` requests** per region in parallel, and takes the median.
3. The lowest-RTT region is preselected for Quick Play and Create Arena. The user can override it in the dialog.
4. Results are cached for 10 minutes and re-measured in the background.

### 8.5 Network tier

- **Premium Tier** (the default). Traffic enters Google's backbone at the edge point of presence nearest the player and travels to the region over Google's network instead of the public internet. This gives lower and more stable RTT.

| `client_resync_total`, `event_replay_total` | counter | spike |

Messaging metrics (Pub/Sub latency, spool, DLQ, rating lag) are listed in [Events §10](./EVENTS-AND-MESSAGING.md#10-observability).

- Metrics are recorded with the **OpenTelemetry** metrics API and exposed on `/metrics` by the Prometheus exporter. Prometheus scrapes them, and Grafana holds the dashboards and the alert rules in the table above ([CI-CD §7](./CI-CD.md#7-rollback-notifications-observability)).
- Hot-path instruments (tick duration, jitter) are created once at startup, with pre-built attribute sets, and are recorded outside `sim.Step`. A benchmark of the full arena tick checks that recording them doesn't allocate.
- Panics and unexpected errors are reported to **Sentry**, tagged with `arenaId` and the release SHA.

### 9.2 Tools
